# Phase 2 모듈 1 — 이벤트(공시) 데이터 수집 진행 보고

생성 시각: 2026-08-12

## 범위 결정: 일반 뉴스가 아니라 공식 공시(disclosure) API

Phase 1 스코프(120종목 × 2015~현재)를 유지하면서 뉴스 감성 신호를 붙이려고
네이버 뉴스 API, 빅카인즈, NewsAPI.org, Alpha Vantage 등을 조사했으나 전체
기간을 무료·합법·재현 가능하게 커버하는 소스가 없었다(상세 근거는
`plan/08_phase2_news_events.md`). 대신 **DART Open API(한국)** / **SEC
EDGAR(미국)** 공식 공시 API를 1차 소스로 채택했다 — KRX Open API 전환 때와
같은 원칙("공식 API가 있으면 스크레이핑하지 않는다").

## KR 매핑 과정에서 발견한 버그 — 우선주 티커

`005935`(삼성전자우), `003545`(대신증권우)가 DART `corpCode.xml`에서 직접
안 잡혔다. 원인 확인: DART는 corp_code를 **법인 단위**로 관리해서, 우선주는
따로 등록되지 않고 보통주(005930/003540)와 corp_code를 공유한다(실제 XML
grep으로 확인). `_match_kr_tickers`에 "직접 매칭 실패 시 마지막 자리를
0으로 바꿔 보통주 코드로 재시도" 폴백을 추가해 해결 — 그래도 못 찾으면
추측하지 않고 missing으로 보고하도록 안전하게 설계.

## KR 수집 과정에서 발견한 버그 — `pblntf_ty`는 응답 필드가 아니라 요청 파라미터

처음에는 전체 공시를 받아온 뒤 클라이언트에서 `pblntf_ty`(공시유형)로
걸러내려 했는데, **DART API 응답의 `list` 배열에는애초에 `pblntf_ty`
필드가 없다** — 요청 시에만 쓰는 필터 파라미터였다(API 문서로 확인).
그 결과 필터가 조용히 무필터로 동작해 대신증권 한 종목만 11,815건(ELS/DLS
같은 파생결합증권 발행 관련 서류가 대부분)이 잡히는 등 노이즈가 심했다.
`pblntf_ty` 값(B, I)마다 별도 요청을 보내는 방식으로 수정해 서버 측에서
필터링하도록 고쳤다 — 그 결과 대신증권은 414건으로 줄었고, `report_nm`
분포를 봐도 실적발표·자사주매입·배당결정·소송 등 실제 "이벤트"성 공시
위주로 바뀌었다(수정 전/후 비교로 검증 완료).

## 실제로 발견한 버그 — SEC ticker→CIK 스냅샷의 함정

`company_tickers.json`은 "현재 시점" 매핑만 제공한다. 60종목 전체의 최초
8-K 날짜를 2015-01-01과 대조하는 감사를 돌렸더니, 지주회사 전환·합병·티커
재사용으로 이력이 통째로 빠지는 사례가 6건 나왔다(전부 SEC 공식 조회로
교차검증 완료):

- **XOM, AVGO, GOOG/GOOGL, FTI, VNOM**: 지주회사 전환·합병으로 CIK가 바뀌어
  최근 CIK만으로는 옛 이력이 빠짐 → 선행 CIK를 찾아 병합.
- **P (가장 심각)**: 2019년 Pandora Media가 Sirius XM에 인수되며 상장폐지된
  뒤, 'P' 티커가 완전히 무관한 회사에 재배정됨. 자동 매칭을 그대로 썼다면
  **다른 회사의 공시를 Pandora 데이터로 착각해 수집할 뻔했다.** 수동으로
  Pandora의 실제 CIK(1230276)로 override.

나머지 8-K 시작일이 늦은 종목들(GKOS, JXN, KNTK, MSGS, NVT, OKTA, PJT, PTGX,
ROIV, TWLO, USFD)은 전부 실제 IPO/스핀오프/SPAC 결성일과 정확히 일치함을
확인해 문제가 아니라고 결론냈다.

**한계**: 이 감사는 현재 60종목 유니버스에 한정된 수동 검증이다. 유니버스가
바뀌면 동일 감사를 다시 해야 한다 — SEC가 CIK 승계 관계를 프로그래밍적으로
제공하지 않아 완전 자동화는 불가능.

## 검증 라운드 1·2 (사용자 요청, 승인 게이트 방식)

### 1차(빠른 훑어보기): 새 버그 없음

4개 모듈 재독 + 120개 raw 파일 전수(스키마/중복키/결측/파일명-ticker 일치) +
CLAUDE.md 사양 대조 + 테스트 74개 — 전부 이상 없음. P(Pandora) 데이터를
직접 열어 파일명 패턴과 마지막 공시 내용(2019-02-05, Sirius XM 인수 완료
시점과 일치)으로 재확인.

### 2차(천천히 디테일하게): 진짜 버그 1건 발견 및 수정

**NYSE 조기마감일 미반영** — `US_MARKET_CLOSE_HOUR_ET=16` 고정 가정이 독립
기념일 전날/추수감사절 다음날/크리스마스이브(13:00 조기마감)를 반영 못 해서,
그 시간대 공시가 "당일"로 잘못 배정될 위험이 있었다. 실제 데이터에서 3건
확인(TSLA·JPM 2017-07-03, VNOM 2019-07-03 — 전부 NYSE 공식 조기마감 공지로
교차검증).

**수정**: 날짜를 하드코딩하지 않고 `trading_days` 캘린더로 "그 공휴일 직전
마지막 거래일"을 계산하는 `_us_early_close_days_for_year()`를 추가해
독립기념일 전날/추수감사절 다음날/크리스마스이브엔 마감 기준을 13:00으로
낮췄다. 하드코딩 대신 캘린더 기반으로 짠 이유는 공휴일이 주말과 겹쳐
관찰일이 밀리는 해가 있기 때문(예: 2026년 7/4가 토요일이라 조기마감이
7/2(목)로 밀림 — NYSE 공식 캘린더로 확인). 신규 테스트 7건(실제 사례 2건 +
회귀 방지용 평일 케이스 + 주말-겹침 엣지케이스 포함) 추가, 전체 81개 테스트
통과.

실제 US 7,944건 전체에 새 로직을 돌려 재검증 — TSLA/JPM/VNOM 3건 모두
`2017-07-05`/`2019-07-05`(다음 거래일)로 올바르게 재배정됨을 확인. 부수적으로
5건에서 "거래일 캘린더 범위 밖" 에러가 났는데, 이건 버그가 아니라 이벤트
데이터(오늘, 2026-08-12까지)가 Phase 1 OHLCV 캘린더(2026-08-10까지)보다
최신이라 생기는 정상적인 경계 상황 — 모듈 4에서 실제 캘린더를 연결할 때
이벤트 수집 시점과 OHLCV 수집 시점을 맞추거나 캘린더 범위를 여유 있게 잡아야
한다는 점을 메모해둔다.

### 2차 재검토(사용자 요청): 진짜 버그 1건 더 발견 및 수정

조기마감 수정 코드 자체를 더 의심스럽게 다시 봤다. 2015~2026년 전 구간에
대해 `_us_early_close_days_for_year()`가 실제로 뭘 계산하는지 전부 출력해서
대조하는 방법으로 검증했는데, **2026년 계산 결과에 `2026-08-10`이라는
말도 안 되는 날짜가 조기마감일로 끼어 있었다.**

**원인**: `_last_trading_day_before(date, trading_days)`가 "캘린더가 아직
그 날짜까지 도달했는지"를 확인 안 하고 있었다. 캘린더가 2026-08-10까지밖에
없는 상태에서 12/25 이전 마지막 거래일을 구하려고 하면, `trading_days <
12/25`가 사실상 캘린더 전체를 통과시켜서 `.max()`가 캘린더의 "현재까지의
마지막 날짜"(8/10)를 반환해버린다 — 이게 우연히 "크리스마스 조기마감일"인
것처럼 잘못 판정됐다.

**영향 방향**: 다행히 조기마감으로 잘못 판정되면 마감 기준이 16:00→13:00으로
낮아지는 쪽이라(더 보수적인 쪽), 실제로 이게 촉발됐다면 누수가 아니라
"과도하게 보수적으로 다음날로 미루는" 방향의 오류였을 것 — 그래도 근거 없는
날짜 판정이라 명백한 버그로 분류하고 고쳤다.

**수정**: `trading_days.max() < date`면 "아직 모름"으로 보고 None을 반환하도록
가드를 추가. 2015~2026년 전체 재검증 결과 2026년만 12월 항목이 정상적으로
빠지고(캘린더가 거기까지 없으므로), 나머지는 전부 기존과 동일하게 유지됨을
확인. 신규 테스트 2건 추가(정확히 13:00 경계 케이스 + 캘린더 미도달 케이스),
전체 83개 테스트 통과. 실제 US 7,944건 재검증도 이상 없음(기존에 확인된
캘린더 범위 밖 5건 제외).

### 2차 세 번째 시도(사용자 요청): 진짜 버그 1건 더 발견 및 수정

이번엔 각도를 바꿔서 (a) 페이지네이션이 정말 빠짐없이 수집됐는지 KR/US
120개 파일 전체를 **실시간 재조회와 대조**하는 방식, (b) 저장된 parquet의
dtype이 파일마다 일관적인지, (c) `event_mapping.py`가 만든 매핑 테이블
120행을 전부 눈으로 훑는 방식으로 검증했다.

**페이지네이션 완전성**: US 60종목은 실시간 SEC 재조회와 accessionNumber
기준으로 100% 정확히 일치. KR은 59/60 일치, 유일한 불일치(015760 한국전력공사,
414 vs 413)는 diff를 떠서 확인해보니 **검토 도중 실제로 오늘(2026-08-12) 새로
올라온 공시**(rcept_no가 `20260812...`) 때문이었다 — 수집 로직 문제가 아니라
데이터가 시간이 지나며 실제로 늘어난 정상적인 상황. 데이터 누락은 0건.

**진짜 버그**: `event_mapping.py`의 `TICKER_CIK_OVERRIDES`가 `cik`만
override하고 `title`은 자동매칭 결과를 그대로 남겨서, ticker "P" 행이
`cik=1230276(Pandora)`인데 `title="Everpure, Inc."`(무관한 회사)로 **한 행
안에서 서로 다른 회사를 가리키는 자기모순** 상태였다. 기능적으로 수집
자체에는 영향 없었지만(코드는 `cik`만 사용, `title`은 표시용), 이 테이블을
사람이 참고하거나 향후 모듈에서 라벨로 쓰면 잘못된 정보가 된다.

**수정**: `TICKER_CIK_OVERRIDES`를 `dict[str, int]`에서 `dict[str, tuple[int,
str]]`(cik+title 동시 override)로 바꾸고, 실제 캐시 파일
(`ticker_cik_map.parquet`)도 재생성해서 `title="Pandora Media, Inc."`로
바로잡았다. 테스트 1건 추가(override가 title까지 바꾸는지 검증), 전체 84개
테스트 통과.

**사소한 것(버그 아님, 조사해서 기각)**: KR `report_nm` trailing whitespace
(모듈 3/4에서 strip 필요), DART `corp_cls`가 코오롱모빌리티그룹만 'E'로
나오는 것(실제론 코스피 맞음, 우리 파이프라인은 이 필드 안 씀), KR `rm` 필드
(시장구분 표시뿐 시각 정보 없음), GOOG/GOOGL 동일 CIK 데이터(같은 법인의
정상 동작), US `items` 코드/통계 이상치(전부 실제 사업 특성으로 설명 가능).

### 2차 네 번째 시도: 새 버그 없음 (클린)

쓰기 원자성(atomic write) 패턴, XOM/VNOM 같은 복잡한 선행 CIK 병합 케이스의
시간순 정합성, KR `flr_nm`≠`corp_name`인 235건의 원인을 각각 확인 — 전부
정상(원자성은 Phase 1과 동일한 기존 관례, 병합은 공백/중복 없이 깨끗함,
`flr_nm` 불일치는 거래소가 직접 발행한 공시라는 정상적인 경우). 새 버그 없음.

### 3차(전체 정독 2~3회): 문서-코드 정합성 3건 + 구조적 공백 1건

코드 자체의 새 버그는 없었지만, CLAUDE.md/plan 문서가 실제 구현을 못 따라간
부분 3곳을 발견해 수정했다: `pblntf_ty` 설명이 "구현 시점 재확인 필요"로
계속 남아있던 것(B/I 확인 완료로 갱신), US 타임스탬프 규칙에 조기마감 예외가
누락돼 있던 것(반영), Phase 2 DoD 체크박스 미갱신(갱신).

더 중요한 발견: **모듈 1 수집을 재현할 오케스트레이션 스크립트가 없었다.**
실제 수집은 이번 세션에서 직접 실행한 1회성 스크립트로만 이뤄졌고,
Phase 1의 `collect.py`/`collect_kr.py`처럼 "유니버스 → 전체 수집"을 한 번에
재현하는 커밋된 코드가 없었다 — 캐시가 유실되거나 유니버스가 바뀌면 처음부터
다시 짜야 하는 상태였다.

## 오케스트레이션 스크립트 정리 (사용자 요청)

`src/data_collection/collect_events.py`를 새로 작성 — `collect_events_us()`/
`collect_events_kr()`가 Phase 1의 `ohlcv_meta_{us,kr}.parquet` 유니버스를
그대로 읽어서 ticker↔CIK/corp_code 매핑 + 전체 이벤트 수집을 한 번에
재현한다(새 유니버스 선정 없음 — Phase 1이 이미 검증한 유니버스를 그대로
재사용). 결합본은 `processed/events_{us,kr}.parquet`에 저장.

재실행으로 검증: 기존 raw 캐시(US 7,944건/KR 22,490건)와 정확히 동일한
건수를 재생산했고, `processed/events_{us,kr}.parquet`의 행 수가 raw 개별
파일 60개씩의 합과 정확히 일치함을 확인. 전체 테스트 84개 통과.

### 3차 재검증(사용자 요청): `collect_events.py` 정독에서 버그 1건 발견 및 수정

새로 추가된 오케스트레이션 스크립트 자체는 아직 상세 리뷰를 거친 적이 없어서
집중적으로 다시 봤다. **Phase 1의 `collect_us()`/`collect_kr()`는 종목 하나가
실패해도 건너뛰고 계속 진행하는데(실패 목록만 기록), `collect_events_us()`/
`collect_events_kr()`는 그런 방어 로직이 없어서 종목 하나만 실패해도(네트워크
타임아웃, API 일시 장애 등) 전체 루프가 죽고 이미 처리한 나머지 종목 결과까지
날아가는** 구조였다. 지금은 전량 캐시 히트라 드러나지 않지만, 캐시 없이 새로
돌리는 시나리오(유니버스 확장 등)에서는 실제로 발생할 수 있는 문제.

**수정**: 종목별 fetch를 try/except로 감싸 실패를 Phase 1과 동일하게 목록으로
수집·로그만 남기고 계속 진행하도록 변경(`fetch_*` 함수들은 성공 시에만
캐시를 쓰므로, 실패한 종목은 다음 실행에서 캐시가 없어 자동 재시도된다).
재실행으로 기존과 동일한 건수(US 7,944건/KR 22,490건) 재생산 확인, 전체
84개 테스트 통과.

추가로 결합본(`processed/events_{us,kr}.parquet`)의 dtype 일관성과
GOOG/GOOGL·005930/005935처럼 CIK/corp_code를 공유하는 티커 쌍이 결합 후에도
여전히 동일한 데이터를 정확히 공유하는지 재확인 — 이상 없음.

### 3차 재검증 두 번째(사용자 요청, "전체적으로 꼼꼼하게"): 코드 중복 1건 + 테스트 공백 1건 발견·수정

이번엔 전 범위를 다시 훑으면서 (a) KR/US 전체 중복 corp_code/CIK가 이미 파악한
것 외에 더 있는지, (b) DART가 주말에 접수된 공시가 있는지(D+1 규칙의 전제
확인), (c) 인증키 누락 시 에러 처리 경로가 테스트됐는지를 봤다.

- 중복 corp_code/CIK: 기존에 파악한 것(005930/005935, GOOG/GOOGL) 외 추가
  발견 없음.
- KR 22,490건 전체에 주말(토/일) `rcept_dt`가 0건임을 확인 — DART가 영업일에만
  접수를 받는다는 D+1 규칙의 전제와 일치.
- **테스트 공백 발견**: `_sec_user_agent()`/DART 키 체크 함수 모두 인증키
  누락 시 에러를 던지는 방어 로직인데 유닛테스트가 하나도 없었다. 테스트를
  추가하려고 보니, `events_kr.py`가 `event_mapping.py`의 `_dart_api_key()`와
  **완전히 동일한 코드를 자체적으로 중복 정의**하고 있다는 것도 함께 발견
  (event_mapping.py에는 원래 이 체크가 인라인으로만 있었음). `events_us.py`가
  이미 `event_mapping.py`의 `_sec_user_agent()`를 import해서 쓰는 것과
  비대칭적인 구조였다.

**수정**: `event_mapping.py`에 `_dart_api_key()`를 정식 함수로 추출하고,
`events_kr.py`는 자체 정의를 지우고 그걸 import하도록 통일(이제
`events_us.py`/`events_kr.py` 둘 다 동일한 패턴으로 `event_mapping.py`의
인증 헬퍼를 재사용). 두 함수(`_sec_user_agent`/`_dart_api_key`) 각각
"키 없으면 에러/키 있으면 반환" 테스트 4건 추가(`monkeypatch`로 환경변수
제어 — 이 프로젝트 테스트에서 처음 쓰는 패턴이라 안전하게 격리되는지 확인
후 적용). 전체 88개 테스트 통과, `collect_events.py` 재실행으로 리팩터링
후에도 동일한 결과(US 7,944건/KR 22,490건) 재생산 확인.
