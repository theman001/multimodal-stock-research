# Review Loop — 수정 내역이 없을 때까지 반복 검토

이 스킬은 코드 리뷰를 "한 번" 하는 게 아니라, **더 이상 고칠 게 없다고 판단될 때까지 여러 라운드를 자동으로 반복**한다. 각 라운드는 이전 라운드의 존재를 몰랐던 것처럼 완전히 새로 시작하는 독립적인 조사여야 한다 — "아까 이미 봤으니까 괜찮겠지"라는 태도가 이 스킬의 가치를 무너뜨린다. 실제로 한 세션에서 7라운드 연속으로 매번 진짜 버그(NAV 오염, 부호 오류, 과도한 예외로 인한 운영 중단, 검증 안 된 외부 입력 등)를 찾아낸 전례가 있다 — "이미 충분히 봤다"는 느낌은 신뢰할 신호가 아니다.

## 검토 대상 정하기

인자로 대상이 주어지면(파일 경로, 디렉토리, "지금 diff" 등) 그것을 쓴다. 없으면:
1. 이 대화에서 방금 작성/수정한 파일들(직전 turn들에서 Edit/Write한 파일)을 대상으로 한다.
2. 그것도 불분명하면 `git status`/`git diff`로 현재 변경분을 확인해 대상으로 삼는다.
3. 그래도 애매하면 사용자에게 물어본다 — 엉뚱한 파일을 검토하며 라운드를 낭비하지 않는다.

## 라운드 하나의 절차

**1. 완전히 새로 정독한다.** 대상 파일(들)을 Read로 처음부터 다시 읽는다. 이전 라운드의 기억에 의존하지 말 것 — 실제로 파일을 다시 열어서 본다.

**2. 매 라운드 다른 각도로 의심한다.** 아래는 실제로 여러 번 진짜 버그를 찾아낸 각도들이다. 매 라운드 최소 2~3개의 다른 각도를 의도적으로 골라 파고든다(매번 같은 각도만 반복하면 새로운 걸 못 찾는다):
   - **경계값/엣지케이스**: 빈 입력, 0, 음수, 정확히 경계선인 값, 첫/마지막 인덱스.
   - **외부 입력 검증**: 이 함수가 받는 값 중 "당연히 정상이겠지"라고 가정한 게 있는가? NaN/Inf/None/음수/타입 불일치가 들어오면 무슨 일이 생기는가? 특히 그 오염이 **한 곳에만 머무르는지, 아니면 신경망 입력처럼 전체를 오염시키는 더 넓은 반경으로 번지는지**를 구분해서 본다.
   - **부호/방향**: 이 값이 반대 방향이면(롱↔숏, 매수↔매도, 증가↔감소) 계산식이 여전히 맞는가? 방향을 가정한 공식을 부호가 다른 입력에 그대로 쓰고 있지 않은가?
   - **통합 지점**: 이 함수가 반환한 값을 다른 함수가 그대로 받아쓸 때, 그 함수의 전제와 이 함수의 출력이 실제로 맞물리는가? (예: A가 "0이면 없음"으로 반환하는데 B가 "0이면 매도 대상"으로 해석)
   - **에러 처리의 반경**: 예외를 던지는 게 맞는가, 아니면 그 지점만 no-op으로 건너뛰는 게 맞는가? 예외가 무관한 나머지 항목/작업까지 막아버리지 않는가? (한 라운드에서 "예외로 막기"가 스스로 만든 새 문제였음을 다음 라운드에서 발견한 전례가 있다 — 방금 만든 수정 자체도 의심 대상이다)
   - **직전 라운드 자신의 수정**: 방금 고친 코드가 새 부작용을 만들지 않았는가? 방금 고친 부분과 다른 부분이 상호작용하는 지점이 있는가?
   - **문서/주석 drift**: 방금 고친 동작과 기존 docstring/주석의 서술이 여전히 일치하는가? (예: "이렇게 하면 자동으로 일반화된다"고 써놨는데 방금 수정으로 그 경로 자체가 없어졌다면 그 문장은 이제 거짓)
   - **최종 출력 자체의 안전성**: 입력만 검증하고 이 함수/파이프라인의 최종 반환값 자체가 유효한지 마지막에 한 번 더 확인하는 방어선이 있는가?
   - **테스트 자체의 신뢰성**: 방금 통과한 테스트가 실제로 그 주장을 검증하는가, 아니면 우연히/공허하게 통과하는가?

**3. 사소한 것은 넘어간다.** 스타일 취향, 네이밍, "이론적으로는 가능하지만 이 시스템 구조상 절대 안 일어나는" 극단적 가정은 고치지 않는다. 실제 트리거 시나리오(입력값 예시, 호출 순서 등)를 구체적으로 설명할 수 있는 것만 고친다.

**4. 문제를 찾으면 고친다.**
   - 코드를 수정한다. 왜 고치는지(트리거 시나리오)를 주석/커밋에 남긴다.
   - 그 버그를 재현하는 회귀 테스트를 추가한다(고치기 전 실패, 고친 후 통과하는지 확인하는 게 이상적).
   - 관련된 다른 파일의 docstring/주석 중 이번 수정으로 사실과 달라진 부분이 있으면 같이 고친다.

**5. 검증한다.**
   - 전체 테스트 스위트를 돌려 통과를 확인한다(프로젝트 테스트 명령을 모르면 CLAUDE.md나 README, 기존 실행 이력에서 찾는다).
   - 프로젝트에 도메인 특화 체크리스트 스킬이 있으면(예: 이 저장소의 `leakage-guard`) 그것도 관련 있는 한 재실행한다.
   - 프로젝트에 진행 로그 관례가 있으면(예: `progress_log.json`, CLAUDE.md의 "진행 로그 프로토콜") 그 라운드의 발견/수정 내역을 한 항목으로 원자적으로 추가한다.

**6. 결과를 간결하게 보고한다.** 다른 설명 없이 이 형식만 출력한다:

```
N차 검토 시작
N차 검토 결과
수정 내역 1
수정 내역 2
```

수정한 게 없으면:

```
N차 검토 시작
N차 검토 결과 수정 내역 없음
```

각 "수정 내역" 줄은 한 문장으로: 무엇이 문제였고 어떻게 고쳤는지만. 발견 과정의 사고 흐름이나 검토한 파일 목록 같은 부가 설명은 넣지 않는다(사용자가 필요하면 따로 물어본다).

## 라운드 반복과 종료

- 한 라운드가 끝나면(수정이 있었든 없었든) **사용자에게 다시 묻지 않고 바로 다음 라운드를 시작**한다 — 이게 이 스킬의 핵심이다("수정 내역이 없을 때까지" 자동 반복).
- 어느 라운드에서 **수정 내역이 없으면 그 즉시 반복을 멈춘다.** 그 라운드까지의 보고를 마지막으로 출력한 뒤, 커밋 여부와 다음 단계 진행 여부를 사용자에게 물어본다(자동으로 커밋하지 않는다 — git 커밋은 항상 명시적 승인 필요).
- 라운드 수에 인위적인 상한을 두지 않는다. 다만 실제로 새로운 것을 찾지 못하는데 보고할 거리를 억지로 만들어내면 안 된다 — "수정 내역 없음"은 유효하고 정상적인 결과다.
- 만약 위험도가 매우 높은 코드(실거래 주문, 자금 이동, 인증/권한 등)를 검토 중이라면 라운드를 더 많이 도는 쪽으로, 단순 스크립트라면 1~3라운드 안에 수렴하는 경향을 자연스럽게 따른다 — 강제로 라운드 수를 맞추려 하지 않는다.
